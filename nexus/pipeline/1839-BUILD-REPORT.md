## What was built

Four targeted fixes to the discovery wizard's answer persistence flow. The primary bug was `OnParametersSet` silently overwriting user-typed answers on every re-render. Three supporting fixes address circuit crash risk, lazy LINQ materialization, and render stability.

---

## Files changed

### `Components/Nexus/DiscoveryStep.razor`
**3 changes:**

1. **`OnParametersSet` — ContainsKey guard (PRIMARY FIX)**  
   Added `if (!_answers.ContainsKey(q.Id))` before restoring from DB. Previously, every re-render (triggered by `StateHasChanged` after user typing) would unconditionally attempt to restore from DB — and if the session object was re-fetched as a new instance, it would overwrite still-valid in-memory values. Now: DB answers only populate `_answers` if the user hasn't typed a value for that question yet.

2. **`HandleContinue` — try/catch + `.ToList()` materialization**  
   Wrapped the save call in try/catch so a DB exception doesn't crash the Blazor circuit. Added `.ToList()` to materialize the LINQ projection before the async `await` — captures a snapshot of `_answers` at the moment Continue is clicked.

3. **`@key="question.Id"` on `DiscoveryQuestionCard`**  
   Added to the `@foreach` loop. Gives Blazor a stable identity for each card across re-renders so MudTextField internal state isn't orphaned when the list re-renders.

### `Services/Discovery/DiscoveryService.cs`
**1 change:**

4. **`SaveAnswersAsync` — answer count logging**  
   Materialized `answers` to `answerList` before the foreach, then added `_logger.LogInformation` with the count and sessionId. This makes zero-save detectable in CloudWatch/logs — previously, if `_answers` was empty, the method would silently do nothing.

## Known edge cases / things Clint should scrutinize

1. **ContainsKey guard and empty-string answers:** If a user types something then clears the field, `_answers[q.Id]` will be an empty string (not absent). `ContainsKey` returns true → DB value won't restore. This is correct behavior (user intentionally cleared). But if CC doesn't call `OnAnswerChanged` for an empty clear (depends on MudTextField behavior), the key may not be present. Low risk — MudTextField fires `ValueChanged` on clear.

2. **try/catch swallows save failure silently:** The catch logs to `Console.Error` but still advances the wizard via `OnCompleted.InvokeAsync()`. User sees no feedback if save fails. This is the spec's decision ("user experience is better than being stuck") — Clint should confirm this is acceptable or flag if a snackbar error is needed.

3. **`DiscoveryQuestionCard.razor` unchanged:** CC confirmed `@key` belongs on the usage site in `DiscoveryStep.razor` (which is where it was added), not inside `DiscoveryQuestionCard` itself. The card component has no looping logic.
